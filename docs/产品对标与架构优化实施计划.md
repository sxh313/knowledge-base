# 知屿产品对标与架构优化实施计划

> 版本：v1.6.25  
> 审计基线：2026-09-05  
> 目标：在不破坏本地优先、用户自行配置模型和 Token 直接粘贴流程的前提下，把知屿从“功能集合”推进为稳定、可演进、可持续交付的学习工作台。

## 1. 审计结论

### 1.1 当前架构优点

- React + TypeScript + Vite 的前端边界清晰，页面、组件、状态、领域逻辑和 Dexie 持久化已经形成基本分层。
- Web/PWA、Electron、Capacitor 共用业务代码，平台差异集中在路由、更新和容器壳层，复用率高。
- Agent 已具备计划解析、工具调用、风险标注、权限、diff、审批、事务、审计、撤销和运行恢复，安全边界明显高于普通聊天式 Agent。
- AI 检索支持关键词、向量、重排、查询改写和联网搜索降级；zero2Review 单独隔离来源和数据域，领域建模方向正确。
- 测试覆盖 Agent、RAG、同步、FSRS、复习编排等核心逻辑，当前基线为 38 个测试文件、232 个测试通过。

### 1.2 不合理或高风险点

1. **全局错误隔离缺失**：任意组件渲染异常都可能让整个 SPA 白屏，用户缺少恢复入口。
2. **AI 请求存在取消竞态**：旧请求被新请求取消后，旧 Promise 的 catch 可能读取新的全局 `AbortController`，从而覆盖新请求的状态。
3. **AI 路由超时边界不完整**：传入外部 signal 时没有内部超时，失败分支的计时器清理也不集中，某些 Provider 卡住时可能长期占用 UI 状态。
4. **双链索引更新不完整**：原逻辑主要在标题/别名改变时更新链接，正文增删 `[[链接]]`、删除目标文档或恢复文档时可能留下过期关系。
5. **Serverless 搜索入口类型边界薄弱**：原入口使用 `ts-nocheck`，Provider、查询长度和异常类型缺少明确约束。
6. **文档与代码发生版本漂移**：README 版本、架构文档 schema 版本与实际代码不一致，发布检查依据不可靠。
7. **端到端冒烟脚本路由过时**：脚本检查已不存在的旧路由，遗漏 Agent、zero2Review、学习和来源页面，容易产生假阳性和假阴性。
8. **状态层职责偏重**：`agentStore`、`JournalEditor`、`SettingsPage` 等文件体积较大，页面编排、异步流程、持久化和错误处理交织，后续迭代成本会持续上升。
9. **发布链路缺少统一入口**：已有 test/build/打包脚本，但缺少一个明确的类型检查、测试、构建串联命令和版本核对步骤。
10. **可观测性仍偏本地**：Agent 有运行事件，但普通 AI 请求、同步和索引任务的耗时/失败原因没有统一的诊断模型。

## 2. 对标成熟产品后的产品原则

知屿不应简单复制某个产品，而应吸收成熟知识工具的共同能力：

- **像 Notion 一样可组织**：页面、属性、视图、模板、任务和搜索需要形成统一对象模型，而不是各自独立入口。
- **像 Obsidian 一样可掌控**：本地数据、双链、反链、来源定位和可迁移性应保持透明，用户可以理解数据在哪里以及如何导出。
- **像 Linear 一样可执行**：Agent 和学习计划需要有明确状态机、操作历史、失败恢复、批量动作和可追踪结果，而非只有聊天记录。
- **像成熟 AI 工作台一样可控**：模型、检索、引用、成本、超时、失败转移和用户审批应可观察、可解释、可回退。

产品优先级应按以下顺序推进：

1. 数据正确性与可恢复性。
2. 高频工作流的速度：捕获、搜索、编辑、复习、Agent 执行。
3. AI 可信度：引用、边界、失败转移、可撤销。
4. 跨设备与跨平台一致性。
5. 扩展能力和视觉细节。

- [x] 修复 `aiStore` 的请求控制器竞态：每次请求持有自己的 controller，旧请求不能覆盖新请求的完成态或错误态。

## 4. 后续实施路线

### Phase A：数据与边界治理

1. 为每个 Dexie 表建立领域 owner 清单，明确 schema、读写入口、同步策略和删除语义。
2. 把 `src/lib/db/queries.ts` 按领域拆成 `journals`、`settings`、`search`、`sync` 访问模块，保留兼容导出，降低单文件耦合。
3. 为双链、软删除、同步合并和索引重建增加集成测试，测试“正文变化、目标改名、目标删除、恢复、并发保存”五类场景。
4. 为导入、同步、索引重建增加幂等键和进度信息；任何后台任务都应能重试且不重复写入。

### Phase B：状态与异步任务治理

1. 抽出 `appBootstrap`，统一设置加载、数据库迁移、索引重建、搜索索引和提醒初始化顺序。
2. 将长流程从页面/store 移入领域服务，store 只保留 UI 状态和命令分发。
3. 建立统一 `AsyncTaskState`：`idle/running/success/error/cancelled`，避免不同页面各自定义 loading/error 语义。
4. 对 AI、同步、导出、索引任务统一提供取消、超时、重试和用户可读错误。

### Phase C：Agent 产品化

1. 将 Agent 运行状态固定为 `planned → approved → running → success/partial/failed/cancelled/rolled_back`，所有状态变化只能通过 transition 函数。
2. 把工具权限拆成“读取范围、写入范围、删除权限、外部网络权限”四个可见维度。
3. 在计划预览中展示影响对象数量、预计耗时、证据来源、可撤销范围和失败处理策略。
4. 增加运行历史过滤、失败重试、仅重试失败操作、复制计划和导出审计记录。
5. 引入离线可用的确定性工具优先策略：搜索、标签、重命名、链接修复等不应为简单操作强制调用模型。

### Phase D：检索与可信回答

1. 为每次检索保存 trace：query、scope、candidateCount、rerank、selectedChunks、latency、fallbackReason。
2. 为回答展示“基于个人笔记/课程资料/网页”的来源分层，不混淆不同可信等级。
3. 对引用定位增加稳定 source anchor 和版本校验；原文变化后明确提示引用可能已失效。
4. 为检索建立离线评测集，至少记录 Recall@K、引用覆盖率、无依据回答率和平均延迟。
5. 对联网搜索加入缓存、域名白名单、抓取超时和正文大小上限，避免单个网页拖垮回答链路。

### Phase E：学习产品闭环

1. 将“捕获 → 整理 → 理解 → 练习 → 复习 → 反馈”作为主任务流，首页突出今日待办而非功能入口。
2. 统一 `LearningGoal`、`LearningTask`、`Zero2ReviewTask` 的状态和统计口径，避免两个学习域出现重复概念。
3. 增加学习任务来源回链：每个任务都能回到课程章节、笔记、卡片或 Agent 运行结果。
4. 统计页从展示数量升级为行动建议：今日优先级、逾期原因、薄弱主题、下次最小行动。
5. 保持复习问答默认本地隔离，只有用户主动开启时才同步正文。

### Phase F：发布与运营

1. 将 `npm run check` 作为所有发布和 PR 的必过门槛。
2. 增加 Web、Electron、Android 三种构建产物的 smoke test；冒烟路由从共享路由清单生成，避免手工漂移。
3. 每次发布自动校验 package、README、CHANGELOG 和 Android versionName 是否一致。
4. 将构建体积、PWA precache 大小、首屏 JS、AI 首 token 延迟纳入发布记录。
5. 为生产错误建立最小诊断格式：版本、平台、路由、任务类型、错误分类、是否可恢复；不得记录 API Key、同步 Token 和完整敏感正文。

## 5. 本轮暂不改变的边界

- 不改动 Token 的直接点击粘贴、当前设备保存和用户自主配置流程。
- 不把 API Key、GitHub Token 或签名材料写入源码、普通备份或构建产物。
- 不把 Electron/Android 重新拆成两套业务前端。
- 不在没有真实用户数据和评测集的情况下擅自调整 FSRS 参数或 AI 质量阈值。

## 7. 验收标准

- 页面渲染异常不会直接白屏，用户至少有重试或重新加载路径。
- 连续快速发起两个 AI 请求时，后一次请求的状态不会被前一次覆盖。
- AI Provider 卡住 60 秒后能结束并进入可理解的失败转移流程。
- 双链正文增删、目标重命名、删除和恢复后，反链与断链结果一致。
- `npm run check` 在干净工作区可重复通过。
- 发布文档中的版本、schema、脚本路由和产物名称与实际代码一致。
